# 이로운사람들 앱 ↔ 회사 전산(CRM) 연동 안내

앱(고객용)과 회사 전산(직원용)을 연결하기 위해 양쪽이 맞춰야 할 내용입니다.
이 문서와 소스에는 비밀번호·API 키·실제 고객 자료가 들어 있지 않습니다.

## 1. 앱 구조 한눈에

- 앱: Expo(React Native) — `artifacts/iroun-benefits`
- 서버: Express 5 + PostgreSQL — `artifacts/api-server` (모든 경로는 `/api/...`)
- 로그인: Clerk. 고객은 휴대폰 번호(문자 인증) 또는 카카오로 가입합니다. 서버는 Clerk가 준 사용자 ID로 고객을 구분합니다.
- 서버 요청 인증: `Authorization: Bearer <Clerk 세션 토큰>`
- 역할: `customer`(고객) / `staff`(직원) / `admin`(관리자) — `iroun_accounts.role`

## 2. 고객을 서로 알아보는 기준

**휴대폰 번호**를 권합니다(숫자만, 예: `01012345678`).
- 앱: 가입 때 인증한 번호(Clerk의 대표 전화번호)
- 전산: 고객 등록 때 적은 번호
- 같은 번호가 전산에 여러 건이면 자동 연결하지 않고 직원이 고르게 해야 합니다.

## 3. 앱이 가진 고객 자료

| 자료 | 위치 | 내용 |
|---|---|---|
| 사업장 조건 | `iroun_accounts.profile.businesses[0]` | industry(업종), province·district(지역), openedYear(개업년도), revenue(매출 구간), employeeBand(직원 수 구간), premises(임차/자가), name(상호) |
| 추가로 답한 조건 | `iroun_accounts.profile.confirmations` | `{ "<조건 열쇠>": { answer: "예"/"아니오", label: "연매출 2억 원 이하" } }` |
| 이용 상태 | `/api/me` 의 `entitlement` | trialActive(체험), contractActive(패키지 계약), subscriptionActive(구독) |
| 패키지 계약 | `iroun_contracts` | user_id, starts_at, ends_at, reason, evidence, revoked_at |
| 회사 신청 도움 요청 | `iroun_service_requests` | benefit_id, kind, state, assigned_to, customer_tasks, internal_note(직원 전용) |
| 문의 | `iroun_inquiries` | title, body, state, replies |
| 정책자금 진단 요청 | `iroun_fund_leads` | phone, name, business_name, answers(매출 3개년·신용점수 구간·대출·연체 등), state, memo(직원 전용) |
| 서류 파일 | `iroun_documents` | name(서류 이름), filename, mime, size (파일 본문은 별도 경로로만 내려받음) |

조건 판단 규칙은 `artifacts/api-server/src/lib/benefit-domain.ts` 에 있습니다.

## 4. 연결하고 싶은 것 (우선순위 순)

1. **전산 → 앱: 패키지 계약자 자동 등록**
   전산에서 계약을 등록하면 앱에서 그 고객이 계약 고객이 됩니다(회사 신청 도움 요청이 열림).
   앱 서버에 추가할 경로(안): `POST /api/integration/contracts` `{ phone, startsAt, endsAt, reason, evidence }` → 그 번호로 가입한 계정에 계약 기록. 아직 가입 전이면 "가입 대기"로 보관했다가 가입 시 연결.
2. **앱 → 전산: 새 고객·요청 전달**
   가입, 조건 선택, 회사 신청 도움 요청, 정책자금 진단 요청이 생기면 전산의 해당 고객에 반영.
   전산에 필요한 경로(안): `POST <전산>/api/app-events` `{ type, phone, name, payload, occurredAt }`
3. **전산 → 앱: 직원이 고친 고객 정보**
   전산에서 고객 조건을 고치면 앱이 다음 조회 때 반영. 고객이 앱에서 직접 고른 값과 다를 때 어느 쪽을 우선할지 정해야 합니다(권장: 가장 최근에 바뀐 값).
4. **고객에게 보여줄 진행 상황**
   전산의 진행 단계 중 고객에게 공개할 항목만 앱의 "회사 진행" 화면에 표시.

## 5. 고객 앱에 절대 내보내지 않을 것

직원 상담 메모, 수수료·계약 금액, 다른 고객 정보, 직원 개인 연락처. 앱 서버도 `internal_note`, 정책자금 `memo` 는 직원에게만 줍니다.

## 6. 서버끼리 인증

- 고객 휴대폰(앱)이 전산을 직접 부르지 않습니다. **앱 서버 ↔ 전산 서버**끼리만 통신합니다.
- 서로 다른 비밀키 2개를 서버 환경 설정에 넣어 사용합니다(앱→전산용, 전산→앱용). 코드나 채팅에 적지 않습니다.
- 요청마다 `X-Timestamp` 와 본문 서명(`HMAC-SHA256`)을 붙이고, 5분이 지난 요청과 같은 `eventId` 의 재전송은 거절합니다.
- 실패한 전달은 보관했다가 다시 보냅니다.

## 7. 전산 쪽에서 알려주면 좋은 것

- 고객 한 명을 나타내는 자료 구조(필드 이름, 전화번호 형식)
- 고객 조회·저장 API 경로와 인증 방식
- 계약(패키지) 자료 구조와 상태 값
- 고객에게 공개해도 되는 진행 단계 목록
- 전산이 돌아가는 주소와, 서버 환경 설정(비밀키)을 넣을 수 있는지 여부

## 2026-10-12 앱 서버 쪽 구현 완료 (전산 → 앱 패키지 계약 자동 반영)

전산이 보낸 규격(`pull`/`ack`, HMAC)대로 앱 서버에 수신을 만들었습니다.

- `src/lib/crm-contracts.ts`: 60초마다 전산에서 변경분을 가져와 한 트랜잭션으로 저장한 뒤에만 `ack`.
- `src/migrations/006-crm-contracts.sql`: `iroun_crm_links`(전산 계약 ↔ 앱 계정, 버전, 상태), `iroun_crm_events`(받은 eventId와 회신 결과). 번호는 원문 없이 해시만 저장.
- 연결 규칙: Clerk **인증 완료된 대표 휴대폰 번호**가 정확히 한 계정과 맞을 때만 최초 연결 → 이후엔 전산 contractId로만 그 계정에 반영(번호로 다시 찾지 않음).
- 가입 전 계약은 `pending_signup`으로 보관 → 고객이 그 번호로 인증 가입하고 앱을 열면(`/me`) 연결.
- 같은 번호 계정 여러 개·연결 계정 삭제·번호 없음 → `review_required`, 자동 부여 안 함.
- 취소/보류는 그 전산 계약의 앱 계약만 멈춤(체험·구독 등은 그대로). 늦게 온 구버전은 무시, 같은 eventId 재수신은 처음 결과 그대로.
- 관리자 확인용: `GET /api/admin/crm-contracts` (번호·메모 없이 연결 상태만).
- 실행 조건: 앱 서버 환경 설정에 `CRM_APP_INBOUND_SECRET`(전산과 같은 64자리 hex)이 있으면 자동 시작. 끄려면 `IROUN_CRM_SYNC_ENABLED=false`. `CRM_BASE_URL` 기본값은 전산 주소.
- 시험: `crm-contracts.test.ts` 14건(가입 후/전 계약, 중복 번호, 연장, 취소, 보류, 구버전 지연, 만료, 확인 전송 실패 후 재수신, 서명 규격).

남은 것: 양쪽 서버에 같은 키 넣기 → 가짜 고객 1~2명으로 실제 확인(`contractActive`).
